## 2. 表总览

  

|   |   |   |   |
|---|---|---|---|
|表|干什么|谁写|谁读|
|`skill`|技能「货架条目」。一个逻辑技能一行，**本身不含版本**|上传（find-or-create、更新展示名/简介/headline）、下载（计数 +1）、技能下架（`hidden=TRUE`）|搜索回表、详情、下载授权|
|`skill_version`|技能的某个具体版本。**能不能下载看这一层**|上传、版本下架（`status='YANKED'`）|搜索（版本投影）、详情（`versions[]`）、下载门禁|
|`skill_file`|版本内每个文件的登记条（路径 / 大小 / sha256 / `storage_key`）|上传、覆盖同名版本时删除|**仅 bundle 丢失的降级路径**|
|`skill_search_document`|搜索用的「目录卡片」，一行一个 skill|发布事务提交后**异步重建**|搜索阶段 ①（决定哪些 id 命中、排第几）|
|`skill_version_stats`|按版本的下载计数，**行是懒创建的**|下载（upsert）|**无读者**（搜索排序用 `skill.download_count`）|

## 3. 表间关系

  

暂时无法在飞书文档外展示此内容

  

|   |   |   |
|---|---|---|
|关系|基数|说明|
|`skill` → `skill_version`|1 : N|一个技能有多个版本|
|`skill.latest_version_id` → `skill_version.id`|N : 1|反向指针，指向「当前该给用户看的那个版本」（详情里的 `headlineVersion`）|
|`skill_version` → `skill_file`|1 : N|一个版本有多个文件登记条|
|`skill` → `skill_search_document`|1 : 1|一个技能一行索引|
|`skill` / `skill_version` → `skill_version_stats`|1 : 0..1|行**第一次被下载时才创建**|

  

**`(owner_id, slug)`** **组合唯一是全平台 URL 解析的唯一依据**：`/api/skills/{owner}/{slug}` 必须对应唯一一行。原平台的唯一键是 `(namespace_id, slug, owner_id)`，带 `owner_id` 导致同一 URL 对不同人可能解析到不同技能，还得写一段没有 `ORDER BY` 的消歧代码；去掉命名空间后这个问题连同那段代码一起消失（27 §3.1）。

  

## 4. 表结构明细

  

### 4.1 `skill` —— 技能货架条目

  

|   |   |   |   |
|---|---|---|---|
|列|类型|应用层规则|含义|
|**id**|BIGSERIAL|主键，数据库生成|内部主键。对象存储 key 里的 `{skillId}` 就是它|
|`owner_id`|VARCHAR(128)|非空；与 `slug` 组合唯一|上传者身份标识，来自网关注入的身份头。**原平台此处的** **`namespace_id`** **由它取代**|
|`slug`|VARCHAR(128)|非空；与 `owner_id` 组合唯一；词法校验|技能短名，URL 里那一段。由 `SKILL.md` 的 `name` 归一化生成（去空格 → 转小写 → 非字母数字转 `-` → 折叠 `-` → 去首尾 `-`；长度 2–64，禁 `--`，禁保留字）|
|`display_name`|VARCHAR(256)|可空|展示名，来自 `SKILL.md` 的 `name`。每次上传覆盖|
|`summary`|VARCHAR(512)|可空|简介，来自 `SKILL.md` 的 `description`。每次上传覆盖|
|`visibility`|VARCHAR(32)|非空，应用层写默认 `PUBLIC`；取值 ∈ {`PUBLIC`, `PRIVATE`}|技能可见性。原平台第三值 `NAMESPACE_ONLY` 已去掉。没有独立修改接口，靠重传新版本变更|
|`status`|VARCHAR(32)|非空，应用层写默认 `ACTIVE`；取值 ∈ {`ACTIVE`, `ARCHIVED`}|技能容器状态。**本平台无接口能改成** **`ARCHIVED`****，恒为** **`ACTIVE`**|
|`latest_version_id`|BIGINT|可空；须指向存在的 `skill_version.id`|当前对外版本。详情与搜索里的 `headlineVersion` 取自它。上传即发布，每次上传都写|
|`download_count`|BIGINT|非空，应用层写默认 0|技能累计下载次数的冗余计数。**搜索** **`sort=downloads`** **按它排序**（不是 `skill_version_stats`）|
|`hidden`|BOOLEAN|非空，应用层写默认 `FALSE`|技能级下架标志。`TRUE` ⇒ 搜不到（含作者）、非作者详情与下载 403；作者本人仍可看可下。**本版本只能置** **`TRUE`****，无恢复接口**|

  

~~**唯一性**~~~~：~~~~`(owner_id, slug)`~~ ~~由应用层保证，无数据库唯一索引~~ ~~**添加唯一索引**~~

**上游行为**：上传时 find-or-create；只有「自动发布或 PRIVATE」才写 `latest_version_id` 与 `visibility`（接口文档 §3.6 给出变通路径：重传新版本携带目标 `visibility` 即可更新）。下架不删任何数据，只翻 `hidden`。

  

### 4.2 `skill_version` —— 技能版本

  

技能的某一个具体版本。**「能不能下载」看这一层**：状态、就绪标志、下架时间都在这里。

  

|   |   |   |   |
|---|---|---|---|
|列|类型|应用层规则|含义|
|**id**|BIGSERIAL|主键，数据库生成|内部主键。对象存储 key 里的 `{versionId}`|
|`skill_id`|BIGINT|非空；须指向存在的 `skill.id`|属于哪个技能|
|`version`|VARCHAR(64)|非空；与 `skill_id` 组合唯一|版本号字符串，如 `1.2.0`。来自 frontmatter；省略时服务端生成 `yyyyMMdd.HHmmss`|
|`status`|VARCHAR(32)|非空，应用层写默认 `DRAFT`；取值 ∈ 8 值枚举|版本生命周期状态。**本平台只写入 2 个**：`PUBLISHED`（上传即发布，唯一入口状态）、`YANKED`（版本下架）。其余 6 值永不产生（§5）|
|`requested_visibility`|VARCHAR(20)|可空|上传时「想要」的可见性快照。与 `skill.visibility` 分开保留，无修改入口|
|`parsed_metadata_json`|JSONB|可空|`SKILL.md` frontmatter 的解析结果（`name` / `description` / `version` 等）|
|`manifest_json`|JSONB|可空|包内文件清单快照 `[{path, size, contentType}]`|
|`file_count`|INT|非空，应用层写默认 0|该版本文件数。详情 `versions[].fileCount`、上传响应 `fileCount` 取自它|
|`total_size`|BIGINT|非空，应用层写默认 0|该版本文件总字节数|
|`bundle_ready`|BOOLEAN|非空，应用层写默认 `FALSE`|整包 zip 是否已生成。本平台在上传事务内同步打包，**恒为** **`TRUE`**|
|`download_ready`|BOOLEAN|非空，应用层写默认 `FALSE`|下载资源是否就绪。本平台**恒等价于** **`published_at IS NOT NULL`**（无异步发布时刻）|
|`published_at`|TIMESTAMPTZ|可空|发布时间。本平台 = 上传成功时间|
|`yanked_at`|TIMESTAMPTZ|可空|版本级下架时间。**非空 ⇒ 该版本永久不可下载**，对所有人（含作者）不可逆|

  

~~**唯一性**~~~~：~~~~`(skill_id, version)`~~ ~~由应用层保证。~~~~添加唯一索引~~

**版本号冲突规则**（接口文档 §3.4）：已存在且已发布 → `400` 报错；已存在但已下架 → **允许覆盖**，旧版本的 `skill_file` 行与对象存储对象先被删除再重建。

  

### 4.3 `skill_file` —— 文件登记条

  

版本内每个文件一行：路径、大小、哈希、以及换字节用的钥匙。**是「数据库只存钥匙」这句话的落点。**

  

|   |   |   |   |
|---|---|---|---|
|列|类型|应用层规则|含义|
|**id**|BIGSERIAL|主键，数据库生成|内部主键|
|`version_id`|BIGINT|非空；须指向存在的 `skill_version.id`|属于哪个版本|
|`file_path`|VARCHAR(512)|非空；与 `version_id` 组合唯一|包内相对路径，如 `SKILL.md`、`main.py`|
|`file_size`|BIGINT|非空|文件字节数|
|`content_type`|VARCHAR(128)|可空|MIME 类型|
|`sha256`|VARCHAR(64)|非空|文件内容哈希，写存储时对内存中的字节现算|
|`storage_key`|VARCHAR(512)|非空|**对象存储的钥匙**：`skills/{skillId}/{versionId}/{包内路径}`|

  

~~**唯一性**~~~~：~~~~`(version_id, file_path)`~~ ~~由应用层保证（解包阶段同一路径只应出现一次）。~~~~**添加唯一索引**~~

**关键语义**：正常下载路径**完全不读本表**（直接取整包 `bundle.zip`）；只有 bundle 丢失的降级路径才读它 → 逐个探测对象是否还在 → 在内存里现打一个 zip 返回。**现打的包不写回对象存储**，所以每次请求都要重读重打（接口文档 §6.6）。

  

### 4.4 `skill_search_document` —— 搜索目录卡片

  

搜索用的读模型投影，一行对应一个 skill。搜索是**两阶段读**：阶段 ① 只查本表拿到「哪些 id 命中、按什么顺序」，阶段 ② 按这批 id 回表读 `skill` / `skill_version` 取真数据。

  

|   |   |   |   |
|---|---|---|---|
|列|类型|应用层规则|含义|
|**skill_id**|BIGINT|一个 skill 一行（应用层保证）；须指向存在的 `skill.id`|自然行标识|
|`owner_id`|VARCHAR(128)|非空|作者标识的冗余列，用于 `owner=` 过滤。原文此处为 `namespace_id`|
|`title`|VARCHAR(512)|可空|标题（展示名冗余），参与检索向量加权|
|`summary`|TEXT|可空|简介冗余|
|`keywords`|TEXT|可空|关键词冗余|
|`search_text`|TEXT|可空|全文检索文本。**中文先经 jieba 分词后写进这里**，补偿 PG `simple` 分词器对中文的不足|
|`visibility`|VARCHAR(32)|非空|可见性冗余列，供 SQL 直接过滤|
|`status`|VARCHAR(32)|非空|状态冗余列，供 SQL 直接过滤|
|`search_vector`|TSVECTOR|应用层在写入时计算并存入|检索向量，配合 GIN 索引做 `@@ to_tsquery('simple', ...)`|

  

**本表没有** **`hidden`** **列** —— 已下架技能靠 JOIN `skill` 时加 `hidden = FALSE` 过滤。

**写入时机是关键**：不在发布链路内，而是**发布事务提交后由事件异步重建**（`afterCommit` + 异步）。由此产生两条语义：**「发布成功 ≠ 立刻搜得到」**；异步任务被丢弃时索引会**永久停留在旧内容**（28 §9.4）。搜索本身是纯读，唯一的写入就是这条异步链路。

  

### 4.5 `skill_version_stats` —— 版本下载计数

  

按版本的下载次数统计。**行是懒创建的** —— 第一次有人下载某个版本时才 insert。

  

|   |   |   |   |
|---|---|---|---|
|列|类型|应用层规则|含义|
|**skill_version_id**|BIGINT|一个版本一行（应用层保证）；须指向存在的 `skill_version.id`|行标识|
|`skill_id`|BIGINT|非空；须指向存在的 `skill.id`|冗余的技能 ID|
|`download_count`|BIGINT|非空，应用层写默认 0|该版本累计下载次数|
|`updated_at`|TIMESTAMPTZ|非空，应用层写入当前时间|最近一次计数更新时间|

  

**写入方式**：原平台用 `INSERT ... ON CONFLICT (skill_version_id) DO UPDATE SET download_count = download_count + 1`（07 §6.6）。**`ON CONFLICT`** **依赖唯一索引才能工作，无约束后必须改写** —— 见 §6.2。

**本表当前没有读者**：搜索排序用的是 `skill.download_count`。保留它属于「照搬原机制、将来少改一处」的选择。

**计数时机**：与 `skill.download_count` 的 +1 **合并为一个事务**，都发生在字节流出之前。因此 302 跳转未真正下载、流中途断开**都会计数**，且没有幂等键、可以被刷（接口文档 §6.5）。

## 5. 枚举与标志位：哪些值实际到不了

  

### 5.1 枚举取值

  

|   |   |   |
|---|---|---|
|枚举|定义的值|实际到达|
|`skill.visibility`|`PUBLIC` / `PRIVATE`|两个都到达|
|`skill.status`|`ACTIVE` / `ARCHIVED`|**只有** **`ACTIVE`** —— 无接口可改为 `ARCHIVED`|
|`skill_version.status`|`PUBLISHED` / `YANKED`|两个都到达|
|`skill_version.status`|`DRAFT` `SCANNING` `SCAN_FAILED` `UPLOADED` `PENDING_REVIEW` `REJECTED`|**永不到达** —— 无审核、无扫描链路|

  

**首次上传不产生** **`DRAFT`****，直接进** **`PUBLISHED`****。**

  

> 这些枚举值现在**只存在于应用层代码里**（数据库是 `VARCHAR`，不声明 `CHECK`），数据库里可能出现的任何字符串都由应用层负责不放进去。

  

### 5.2 恒真 / 恒假清单

  

  

|   |   |   |
|---|---|---|
|列|常态|原因|
|`skill.status`|恒 `ACTIVE`|无接口能改成 `ARCHIVED`|
|`skill.hidden`|恒 `FALSE`，除非技能级下架|下架只能置 `TRUE`，本版本无恢复接口|
|`skill_version.bundle_ready`|恒 `TRUE`|上传事务内同步打包，无异步阶段|
|`skill_version.download_ready`|恒 `= published_at IS NOT NULL`|没有由扫描/审核回写产生的发布时刻|
|`skill_version.requested_visibility`|恒 = 上传时携带的 `visibility`|无修改入口|

## 6. 对象存储 key 布局（与表配套）

  

数据库只存钥匙，字节在对象存储里。key 只有两种形状：

  

|   |   |   |   |
|---|---|---|---|
|key|内容|写|读|
|`skills/{skillId}/{versionId}/{包内路径}`|单个文件的字节|上传|**仅降级路径**逐个探测是否还在|
|`packages/{skillId}/{versionId}/bundle.zip`|整包 zip（服务端现打，非用户上传的原件）|上传|正常下载路径|

  

两条要记住的：

  

- **key 里只有数字 ID，没有** **`owner`** **/** **`slug`** —— 存储层压根不知道 `alice/weather` 是什么，所以必须先落库拿到 `skillId` / `versionId` 才能构造 key。
    
- **用户上传的原始 zip 不保留**，`bundle.zip` 是服务端用 `ZipOutputStream` 现打出来的（上传时打一次，bundle 丢了则在降级路径上再打，不写回）。
